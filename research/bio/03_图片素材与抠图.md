# 生物地球仪 —— 图片素材与抠图技术调研

调研目标:给 3D 地球上"几百个动植物代表图标"找图,要求最终都是**透明背景可叠加**的图。本报告列出素材源、可验证的 API 调用方式、许可要点,以及本地批量抠图的技术方案。所有标注"已实测"的 URL 均在写报告当天用 `curl` 直接验证过返回内容(不是道听途说)。

---

## TL;DR —— 最省事的透明素材路线

**一句话结论:PhyloPic 是唯一"天生透明 + 有正经 API + 零版权顾虑 + 覆盖上千物种"的源,应作为主力;覆盖不到的物种,退到 iNaturalist 抓照片 + 本地 rembg(`isnet-general-use` 模型)批量抠图。**

推荐管线(按优先级尝试,逐级 fallback):

1. **PhyloPic**(黑色剪影风格,天生透明 PNG/SVG,CC0/PD 为主)—— 用物种学名查,查不到就退到上一级分类阶元(属/科)的剪影兜底,**同一物种若查不到剪影,PhyloPic 对更高阶元(科/目)也常有剪影**,可用来兜底。
2. 查不到剪影 → **iNaturalist API** 抓一张 `photo_license` 为开放许可的实拍照片 → 本地 **rembg**(`isnet-general-use` 或 `birefnet-general` 模型)抠图。
3. iNaturalist 也没有 → **Wikidata 的 P18(image)声明** 拿该物种词条编辑精选的代表图(Commons 一张图)→ 同样丢给 rembg 抠。
4. **BHL 古典博物画**、**Wikimedia Commons 透明分类**、**Twemoji/Noto 表情**、**openclipart/SVG Repo** 都只适合当**装饰性补充或"精选出场物种"的手工加工**,不适合当几百个物种的自动化主力源(理由见下文各节)。

风格提示:PhyloPic 剪影风格统一(纯黑/纯色剪影),几百个图标混在地球上时视觉一致性远好于"剪影+实拍照片抠图"混搭;如果不追求写实,优先全用 PhyloPic,缺图的物种宁可换一个近缘种也别轻易混入实拍抠图,除非你想要的就是照片质感。

## 一、已经是透明背景、可直接用的素材源

### 1.1 PhyloPic(phylopic.org)—— 首选

**是什么**:公有领域/CC 授权的生物学剪影图库,专门给系统发生学、生态学配图用,黑色/纯色剪影,天生透明背景 PNG + SVG。数据库当前约 **12,863 张剪影**(实测 API 返回值)。

**API 基本情况(已实测)**:
- API 根:`https://api.phylopic.org`
- 文档入口:`http://api-docs.phylopic.org/v2/`(本次抓取被服务器拒绝两次,建议直接浏览器打开;实际调用方式已通过 recipes 页 + 实测反推验证)
- Recipes / 示例:`https://www.phylopic.org/articles/api-recipes`
- 许可说明页:`https://www.phylopic.org/articles/image-usage`
- **完全支持 CORS**(`access-control-allow-origin: *`,已实测响应头),意味着网页前端 JS 可以直接调用,不需要后端代理。
- **不需要 API Key。**

**关键坑:`build` 参数**。所有请求都要带 `build=<当前构建号的正整数>`,官方 recipes 页给的示例写的是 `build=NaN`,实测直接会 400:

```
GET https://api.phylopic.org/images?build=NaN&page=0
→ 400 {"build":545,"errors":[{"developerMessage":"Expected a positive integer.", ...}]}
```

**但错误响应体里的 `"build":545` 就是当前真实构建号**——实践中可以先随便发一个请求触发 400,从错误体里读出当前 `build` 值,后续请求都带上这个数字(生产环境建议做成"请求失败自动重试一次并解析 build"的小函数,因为这个号会随官方发版变化)。

**已验证成功的完整调用链**(以狮子 *Panthera leo* 为例,`build=545` 是实测当天的值):

1. 先用 GBIF 把学名转成分类单元 ID(GBIF 覆盖面比 PhyloPic 自带的名称搜索更全,作为中间桥梁最稳):
   ```
   GET https://api.gbif.org/v1/species/match?name=Panthera%20leo
   → {"usageKey":5219404,"scientificName":"Panthera leo (Linnaeus, 1758)", ...}
   ```
2. 用 PhyloPic 的 `resolve` 端点把 GBIF 的 usageKey 换成 PhyloPic 的节点 UUID(**已实测**,这是最可靠的查找方式,比直接用 `filter_name` 模糊搜靠谱):
   ```
   GET https://api.phylopic.org/resolve/gbif.org/species?build=545&objectIDs=5219404
   → {"href":"/nodes/9facf67f-1b39-4be7-8eb5-95dd6905a6e1","title":"Panthera leo"}
   ```
3. 用节点 UUID 拉该物种下所有剪影图(`embed_items=true` 直接把图片详情内嵌进来,省一次请求):
   ```
   GET https://api.phylopic.org/images?build=545&filter_node=9facf67f-1b39-4be7-8eb5-95dd6905a6e1&page=0&embed_items=true
   ```
   返回的每张图(节选真实字段):
   ```json
   {
     "license": {"href": "https://creativecommons.org/publicdomain/zero/1.0/"},
     "attribution": "Margot Michaud",
     "uuid": "76a5e7ce-53fa-46ae-af9e-fabd8b863dcf",
     "_links": {
       "vectorFile": {"href": "https://images.phylopic.org/images/76a5e7ce-53fa-46ae-af9e-fabd8b863dcf/vector.svg"},
       "rasterFiles": [
         {"href": "https://images.phylopic.org/images/76a5e7ce-53fa-46ae-af9e-fabd8b863dcf/raster/1536x1149.png"},
         {"href": "https://images.phylopic.org/images/76a5e7ce-53fa-46ae-af9e-fabd8b863dcf/raster/1024x766.png"},
         {"href": "https://images.phylopic.org/images/76a5e7ce-53fa-46ae-af9e-fabd8b863dcf/raster/512x383.png"}
       ],
       "thumbnailFiles": [
         {"href": "https://images.phylopic.org/images/76a5e7ce-53fa-46ae-af9e-fabd8b863dcf/thumbnail/192x192.png"}
       ]
     }
   }
   ```
   `rasterFiles`/`vectorFile` 里的 URL **可以直接拿来当 `<img src>` 用**,已经是透明背景 PNG(黑色剪影)或纯黑 SVG,不需要任何处理。

**按名称直接搜(不经过 GBIF 桥接)**:也存在 `GET /nodes?filter_name=<名称>&build=<build>&page=0`,官方 recipes 页给的例子是 `filter_name=primates`(用的是俗名/属名,不一定精确匹配学名全称);实测直接传完整学名 `Panthera%20leo` 会返回"page out of bounds"(即该模糊匹配算法没命中),所以**批量脚本建议走上面 GBIF→resolve 的桥接方式**,比直接猜 `filter_name` 稳定得多。

**分类阶元兜底**:PhyloPic 的图片挂在"节点"(node)上,节点可以是种、属、科等任意分类阶元,所以物种一级没有剪影时,同一 `resolve` 链路换成属/科的 GBIF usageKey 往往能拿到"近似长相"的剪影兜底(比如某个具体鼩鼱种没有,但鼩鼱科有)。

**许可(实测 `image-usage` 页)**:数据库里混合了几种 CC 许可,**务必逐图检查 `license` 字段再决定能不能用**:

| 许可 | 是否需要署名 | 能否商用 |
|---|---|---|
| Public Domain Mark (PDM) | 否 | 可以 |
| CC0 1.0 | 否 | 可以 |
| CC-BY 3.0 / 4.0 | **需要**,附许可链接 | 可以 |
| CC-BY-SA 3.0 | **需要** + 同款传播(ShareAlike) | 可以 |
| CC-BY-NC 3.0 / CC-BY-NC-SA 3.0 | 需要 | **不可商用** |

批量拉图时建议在代码里过滤:只保留 `license.href` 落在 `publicdomain/zero` 或 `publicdomain/mark` 或 `licenses/by/` 前缀的,跳过 `-nc-` 的。

### 1.2 Wikimedia Commons 透明背景 PNG 分类

**分类树**(已实测浏览):`Category:Animals on transparent background` 及其子分类,总计 **264 个文件**:

- Animal icons(23)、Cats on transparent background(29)、Dogs with transparent background(20)、Fish on transparent background(48)、Gastropoda with transparent background(15)、Dinosaurs on transparent background(5)、Paleo-illustrations by Entelognathus(44)、People with transparent background(157,与动植物无关)

**结论:这个分类树体量太小(去掉人物类实际动物相关也就一百多张),且是社区随手传的大杂烩(格式混杂 PNG/SVG/GIF/WEBP,画风不统一),不足以支撑"几百个物种"的量,只能当补充/装饰,不能当主力源。**

**API 批量检索(已实测可用)**:
```
GET https://commons.wikimedia.org/w/api.php?action=query&list=categorymembers&cmtitle=Category:Animals_on_transparent_background&cmtype=file&cmlimit=50&format=json&origin=*
```
返回文件标题列表,翻页用响应里的 `continue.cmcontinue` token 拼到下一次请求的 `&cmcontinue=` 参数上。拿到文件名后再用 `prop=imageinfo` 查具体许可和直链:
```
GET https://commons.wikimedia.org/w/api.php?action=query&titles=File:XXX.png&prop=imageinfo&iiprop=url|extmetadata&format=json&origin=*
```
（`&origin=*` 是让浏览器端 JS 直接跨域调用的技巧,已实测返回 `access-control-allow-origin: *`。)

### 1.3 openclipart / SVG Repo / Twemoji / Noto Emoji

**openclipart.org**:全站 **CC0**(公有领域声明),18万+ SVG,有 animals 标签/分类,站点当前可访问(实测 200)。**但官方文档过去提到的 `/search/json/` 检索接口已经失效**——实测请求会跳转回普通网页(302 → 首页 HTML),不再返回 JSON。也就是说**目前没有可用的公开批量检索 API**,只能人工在网页上浏览下载,不适合批量抓几百张。

**SVG Repo(svgrepo.com)**:号称 50 万+ 图标,大部分标注 CC0、允许商用免署名,但**没有公开的官方批量检索 API**,且个别图标可能是其它许可(需逐个查看图标页面的许可说明)。只适合手工挑选个别"标志性图标"用,不建议写爬虫批量抓(有站点条款风险)。

**Twemoji(前 Twitter/现 X 的 emoji 集)**:CC-BY 4.0,需署名。可直接用 jsDelivr CDN 拼 URL:`https://cdn.jsdelivr.net/gh/twitter/twemoji@latest/assets/svg/<unicode码点>.svg`。GitHub 仓库:`https://github.com/twitter/twemoji`。**但 emoji 集里动植物 emoji 只有一百多个(狮子/大象/猫/狗/各类花草……),覆盖的是"标志性大类"而不是具体物种**,只能给地球上少数几个"图例/大类节点"用,不能覆盖几百个具体物种。

**Noto Emoji(Google)**:同样是 emoji 集,图形资源 **Apache 2.0**(比 Twemoji 的 CC-BY 更宽松,几乎不需要在 UI 里挂署名),仓库 `https://github.com/googlefonts/noto-emoji`。覆盖面和用途跟 Twemoji 一样有限,可以作为 Twemoji 的替代/补充,同样只适合"大类图例"。

### 1.4 Biodiversity Heritage Library(BHL)古典博物画 —— 重要澄清:**不是透明背景**

这一条需要先纠正一个常见误解:BHL 的古典博物画确实**版权上是公有领域**(几乎全部书目出版于 1923 年前,美国法律下明确 PD),但它们是**从纸质书扫描下来的整页图像**,背景是米黄/泛黄的纸张纹理,**不是透明的**,拿来用之前必须自己抠图/裁切。所以严格按你要的"已经是透明背景可直接用"分类,BHL 其实该归到"需要自行抠图"那一类,但考虑到它是稀缺的复古博物画风格素材,这里单独放在这一节详细说明。

**三条访问路径**:

**(A)BHL 官方 REST API v3**(已实测端点存在,返回值确认需要 key):
- Base:`https://www.biodiversitylibrary.org/api3`
- 申请免费 Key:`https://www.biodiversitylibrary.org/getapikey.aspx`
- 调用方式:`&apikey=<key>&format=json`,已实测无 key/假 key 时返回:
  ```json
  {"Status":"unauthorized","ErrorMessage":"'' is an invalid or unauthorized API key.","Result":"..."}
  ```
- 关键操作:`op=GetNameMetadata&name=<学名>`(按学名查,返回关联的 ItemID/PageID)、`GetPageMetadata`(页面级信息+OCR文字)、`GetItemMetadata`(整卷/整本元数据)。
- **拿页面图直接下载**(已实测):
  ```
  GET http://www.biodiversitylibrary.org/pageimage/<PageID>
  → 302 重定向到 https://bhl-open-data.s3.us-east-2.amazonaws.com/web/.../xxx_full.webp
  ```
  即 2024 年后 BHL 图像已经迁到 AWS S3(见下方 C)。
- 局限:API 返回的是"整页"而非"单独裁好的插画",一页扫描里可能大部分是文字、图版只占一角,批量脚本拿到的是全页图,想要单独的动植物图仍需人工裁切+抠图。

**(B)BHL 的 Flickr 相册**(更适合找"已经大致裁好的插画",实测 25万+ 张图):
- 相册页:`https://www.flickr.com/photos/biodivlibrary/`
- 官方说明"BHL Flickr 里的图都可自由浏览、下载、再利用"(公有领域标记为主),按 Album(对应每本书)、Collection(主题合集,如植物画、海洋生物、濒危物种)两种方式组织,约 18% 已被志愿者打上物种/画师/地点标签。
- 用 Flickr 官方 API 批量检索(需要免费 Flickr API Key,`https://www.flickr.com/services/api/`):
  ```
  https://api.flickr.com/services/rest/?method=flickr.people.findByUsername&username=biodivlibrary&api_key=<key>&format=json
  ```
  先拿到 BHL 账号的数字 NSID,再:
  ```
  https://api.flickr.com/services/rest/?method=flickr.photos.search&user_id=<NSID>&tags=<物种名或俗名>&api_key=<key>&format=json&nojsoncallback=1
  ```
- 这条路线拿到的图通常已经是"图版级别"的裁剪(而不是整页文字+图混杂),质量上比方案 A 更适合本项目,但仍然是纸张背景,还是要抠图。

**(C)BHL Open Data on AWS(2024 起,批量/离线场景用)**:
- 2024 年 BHL 加入 AWS Open Data 赞助计划,全量元数据 + JPEG2000 页面图 + OCR 文本都放在 S3,bucket `arn:aws:s3:::bhl-open-data`(us-east-2 区域),元数据每月更新、图片每周更新。
- 数据字典/说明:`https://github.com/gbhl/bhl-open-data`,注册页:`https://registry.opendata.aws/bhl-open-data/`
- 适合"离线批量下载一大批页面图自己处理"的场景,不需要逐条调 API、不受 key 限流,但同样是整页图,不是预裁剪的插画。

**版权提醒**:BHL 里绝大多数内容确实公有领域,但**并非全部**——个别较新卷册可能仍在版权期内,`GetItemMetadata` 返回里会有 Rights 相关字段,批量抓取前建议只保留出版年份早于 1929 年(美国公有领域安全线)的条目,或者以 Flickr 上标注的 Public Domain / No known copyright restrictions 为准。

**给这个项目的实际建议**:BHL 素材质感独特(手绘博物画风格),适合挑几个"重点展示物种"手工精修(下载 Flickr 图版 → 手动裁切 → rembg 或手动抠图),但**不建议**作为几百个图标的自动化主力源——人工介入成本太高,产出速度远不如 PhyloPic 剪影或 iNaturalist 实拍+自动抠图的组合。

## 二、照片源 + 需自行抠图

### 2.1 iNaturalist API

**基本情况**:公民科学平台,数亿张物种观测照片,API 完全公开、**已实测支持 CORS**(`access-control-allow-origin: *`),GET 类检索不需要 API Key。

**Base**:`https://api.inaturalist.org/v1`,文档:`https://api.inaturalist.org/v1/docs/`

**按学名查物种(已实测)**:
```
GET https://api.inaturalist.org/v1/taxa?q=Panthera%20leo&rank=species
```
返回(节选真实字段):
```json
{
  "id": 41964, "name": "Panthera leo", "preferred_common_name": "Lion",
  "default_photo": {
    "license_code": "cc-by-nc-nd",
    "attribution": "(c) seasav, some rights reserved (CC BY-NC-ND), uploaded by seasav",
    "square_url": "https://inaturalist-open-data.s3.amazonaws.com/photos/9225318/square.jpg",
    "medium_url": "https://inaturalist-open-data.s3.amazonaws.com/photos/9225318/medium.jpg"
  },
  "wikipedia_url": "http://en.wikipedia.org/wiki/Lion",
  "observations_count": 24041
}
```
**注意**:`default_photo` 不一定是开放许可(上例正是 CC-BY-NC-ND,不可商用/不可改作,不能直接拿来抠图放到你的产品里)!必须再查 `observations` 端点,按许可过滤:

```
GET https://api.inaturalist.org/v1/observations?taxon_id=41964&photo_license=cc0,cc-by,cc-by-sa&quality_grade=research&per_page=30
```
`photo_license` 支持逗号分隔多个值:`cc0` / `cc-by` / `cc-by-sa` / `cc-by-nc` / `cc-by-nd` / `cc-by-nc-sa` / `cc-by-nc-nd` / `any` / `none`。**每张照片的许可要从返回结果里 `observation.photos[].license_code` 逐张确认**,同一条 observation 下多张照片许可可能不同。

**图片尺寸规则**(已确认):`https://[static.inaturalist.org 或 inaturalist-open-data.s3.amazonaws.com]/photos/<photo_id>/<size>.<ext>`,`size` 可选 `square`(75×75)/`small`(≤240px)/`medium`(≤500px)/`large`(≤1024px)/`original`(≤2048px)。做地球图标一般 `medium` 或 `large` 就够,抠图输入建议用 `large` 保留更多细节方便精细抠边。

**署名格式**:直接采用返回字段 `attribution`(形如 `"(c) 用户名, some rights reserved (CC BY), uploaded by 用户名"`),原样保留即可满足署名要求。

### 2.2 Wikimedia Commons 常规照片(按物种名取代表图)

有两条实测都通的路径:

**路径 A —— Wikipedia `pageimages`(简单但需要处理跳转/取名问题)**:
```
GET https://en.wikipedia.org/w/api.php?action=query&titles=Lion&prop=pageimages&format=json&pithumbsize=300&redirects=1
→ {"thumbnail":{"source":"https://upload.wikimedia.org/.../330px-....jpg","width":300,"height":200}}
```
注意这是 **en.wikipedia.org** 的接口,不是 commons.wikimedia.org(Commons 的文件页没有"pageimage"概念);实测直接传学名 `Panthera leo` 查不到缩略图,换成俗名 `Lion` 才有——**批量脚本建议先用 Wikidata 把学名转成对应语言维基百科的词条标题,而不是直接猜俗名**。

（题外提醒:早期 REST API 的 `/page/media` 及 `/page/media-list` 端点已被 Wikimedia 正式弃用下线,搜索官方弃用公告确认了这一点,现在应该用上面的 `action=query&prop=pageimages`,或下面路径 B 的 Wikidata P18 方案,而不是照搬网上一些教程里还在用的 `media-list`。)

**路径 B —— Wikidata 的 P18(image)声明,更适合批量抓"编辑精选代表图"**:
每个物种在 Wikidata 上的条目(用学名 P225 能查到对应 Q 号)常有 `P18`(image)声明,指向 Commons 上编辑公认的代表图。拿到文件名后用 **`Special:FilePath` 直链**(已实测,是最省事的取直链方式,不需要拼 upload.wikimedia.org 的哈希路径):
```
GET https://commons.wikimedia.org/wiki/Special:FilePath/<文件名>
→ 302 → 301 → 最终 https://upload.wikimedia.org/wikipedia/commons/x/xx/<文件名>
GET https://commons.wikimedia.org/wiki/Special:FilePath/<文件名>?width=300   # 加 width 参数直接拿缩略图
```
配合 `action=wbgetclaims&property=P18&entity=<Q号>` 或直接读 `https://www.wikidata.org/wiki/Special:EntityData/<Q号>.json`(已实测可正常访问)解析 `claims.P18[0].mainsnak.datavalue.value` 拿文件名。

**许可与署名**:Commons 每个文件页都有独立许可(多为 CC-BY-SA / CC-BY / PD,少数全版权禁用),批量用之前要用 `prop=imageinfo&iiprop=extmetadata` 查 `LicenseShortName`/`Artist`/`Credit` 字段,自动生成署名文案。

### 2.3 GBIF occurrence 关联图片

**GBIF** 本质是"物种分布记录聚合器",图片大多是从 iNaturalist、各博物馆标本库等源头转载来的,适合查漏补缺(标本照片、iNaturalist 没有的冷门物种)。

**学名转 ID(已实测)**:
```
GET https://api.gbif.org/v1/species/match?name=Panthera%20leo
→ {"usageKey":5219404, "canonicalName":"Panthera leo", ...}
```

**查带图片的观测记录(已实测)**:
```
GET https://api.gbif.org/v1/occurrence/search?scientificName=Panthera%20leo&mediaType=StillImage&limit=20
```
返回的每条记录里 `extensions."http://rs.gbif.org/terms/1.0/Multimedia"` 数组包含真实图片直链、许可、版权方,例如实测拿到一条:
```json
{
  "http://purl.org/dc/terms/type": "StillImage",
  "http://purl.org/dc/terms/license": "https://creativecommons.org/licenses/by-nc/4.0/",
  "http://purl.org/dc/terms/identifier": "https://inaturalist-open-data.s3.amazonaws.com/photos/604437711/original.jpg",
  "http://purl.org/dc/terms/rightsHolder": "jniff"
}
```
（可以看到这条记录本质是转载自 iNaturalist,许可是 CC-BY-NC——**GBIF 官方文档明确提示"occurrence 图片可能比记录本身的许可更严格",每条都要单独检查 license 字段,不能假设整体开放。**)

**图片代理/缩放服务**(Thumbor):
```
https://api.gbif.org/v1/image/cache/occurrence/<gbifID>/media/<md5(identifier)>
https://api.gbif.org/v1/image/cache/200x/occurrence/<gbifID>/media/<md5(identifier)>   # 200px 宽缩略图
```
最大 1200×1200,JPEG 质量上限 85。

**结论**:GBIF 对这个项目主要是"iNaturalist 之外的补充源",直接查 iNaturalist 效率更高;GBIF 的价值在于能搜到 iNaturalist 覆盖不到的标本类/学术数据源图片。

## 三、本地批量抠图技术方案(Windows + Python 3.12)

### 3.1 rembg —— 首选

- GitHub:`https://github.com/danielgatis/rembg`(MIT 许可,作者 Daniel Gatis)
- PyPI:`https://pypi.org/project/rembg/`,要求 `Python >=3.11,<4.0`,**与本机 Python 3.12 兼容**。

**安装**(纯 CPU,最省事;有独显走 GPU 分支更快):
```powershell
pip install "rembg[cpu,cli]"
# 有 NVIDIA 显卡且装好 CUDA/cuDNN:
pip install "rembg[gpu,cli]"
```

**模型选择**(首次使用自动下载到 `~\.u2net\`,即 `C:\Users\<用户>\.u2net\`):

| 模型 | 体积 | 特点 |
|---|---|---|
| `u2net` | ~176MB | 默认通用模型,速度和质量均衡 |
| `u2netp` | 更小 | u2net 轻量版,更快但精度略降 |
| `silueta` | ~43MB | u2net 压缩版,体积小 |
| **`isnet-general-use`** | ~179MB | 较新的通用模型,边缘更干净,**推荐作为本项目默认模型** |
| `isnet-anime` | — | 专攻动漫/扁平色块插画,如果地球图标走卡通风格可以试 |
| `birefnet-general` / `birefnet-general-lite` | 较大 | rembg 内置的 BiRefNet 导出版,细节(绒毛/触角/花蕊)更好但更慢,适合对少量"精修"图标二次处理 |
| `bria-rmbg` | — | rembg 内置的 BRIA RMBG 集成,**⚠️ 继承 BRIA 的非商用许可限制**(见下节许可表),商用/公开项目慎用 |

**命令行批量处理**(整个文件夹):
```powershell
# 用推荐模型批量处理
rembg p -m isnet-general-use .\photos_raw .\photos_cutout

# 需要更精细的毛发/边缘,开启 alpha matting 精修
rembg p -m isnet-general-use -a -af 240 -ab 10 -ae 10 .\photos_raw .\photos_cutout

# 监听模式:新丢进 input 文件夹的图自动处理
rembg p -w .\photos_raw .\photos_cutout
```
（`-a` 开启 alpha matting,`-af`/`-ab`/`-ae` 分别是前景阈值/背景阈值/腐蚀大小,默认 240/10/10。)

**Python 脚本示例**(批量处理 + 复用模型会话提速):
```python
from rembg import remove, new_session
from PIL import Image
import pathlib

session = new_session("isnet-general-use")  # 只加载一次模型,重复调用更快
src_dir = pathlib.Path("photos_raw")
dst_dir = pathlib.Path("photos_cutout")
dst_dir.mkdir(exist_ok=True)

for f in src_dir.glob("*.jpg"):
    img = Image.open(f)
    out = remove(
        img,
        session=session,
        alpha_matting=True,
        alpha_matting_foreground_threshold=240,
        alpha_matting_background_threshold=10,
        alpha_matting_erode_size=10,
    )
    out.save(dst_dir / f"{f.stem}.png")
    print(f"done: {f.name}")
```

**算力需求**:CPU 即可处理几百张图(`u2net`/`isnet-general-use` 单张约 1-3 秒),不需要显卡;有独显(哪怕入门级 4GB 显存)能提速 5-10 倍,处理 `birefnet-general` 这类更重的模型时收益更明显。

### 3.2 其它抠图方案对比

| 方案 | 许可 | 质量 | 易用性 | 备注 |
|---|---|---|---|---|
| **rembg + isnet-general-use** | MIT | 良好 | ★★★★★ 开箱即用 CLI/批量 | 本项目首选起点 |
| **rembg + birefnet-general** | MIT(继承 BiRefNet) | 更好(细节强) | ★★★★ | 速度较慢,适合对少量图精修 |
| rembg + bria-rmbg | ⚠️ 非商用 | 高 | ★★★★ | 继承 BRIA 许可限制,见下 |
| **BiRefNet 原生仓库**(`github.com/ZhengPeng7/BiRefNet`) | **MIT** | 目前公认最强之一,支持到 2048×2048 无拼接痕迹 | ★★★(需要自己写 HF `transformers`/仓库脚本调用) | 追求极致质量、愿意折腾时用 |
| **RMBG-2.0**(BRIA AI,`huggingface.co/briaai/RMBG-2.0`) | **CC BY-NC 4.0,非商用**;商用需另购 BRIA 商业授权 | 很高 | ★★★ | ⚠️ 公开/商业网页慎用,除非确认走非商用授权范围或额外付费 |
| RMBG-1.4(同上,旧版) | ⚠️ 同样非商用许可协议 | 中高 | ★★★ | 同上 |
| **transparent-background**(InSPyReNet,`github.com/plemeri/transparent-background`) | **MIT** | 良好,高分辨率图表现不错 | ★★★★(`pip install transparent-background`,自带 CLI) | ACCV 2022 论文模型,活跃维护(累计 500万+ 下载),MIT 全商用友好,可作为 rembg 的平替/交叉验证 |

**license 要点单独强调**:BRIA 的 RMBG-1.4/2.0 都是"非商用许可(Non-Commercial)",Hugging Face 模型卡上明确写"Creative Commons license for non-commercial use, commercial use subject to a commercial agreement with BRIA"——如果这个生物地球仪网页将来有任何商业化可能(广告、付费、公司项目展示),不要直接用 RMBG 系列,改用 MIT 的 `isnet-general-use`(rembg 自带)或 **BiRefNet**(MIT)。

**给本项目的实操建议**:批量用 `rembg` + `isnet-general-use` 过一遍所有 iNaturalist/Wikimedia 抓来的照片;挑出抠得不好的(比如腿很细的鸟、须状触角的昆虫)用 `rembg -m birefnet-general` 或 `transparent-background` 单独重跑一次做精修,两者都是 MIT 许可,不用操心版权。

## 四、许可总表

| 素材源 | 是否天生透明 | 典型许可 | 能否用于公开网页 | 署名要求 |
|---|---|---|---|---|
| **PhyloPic** | ✅ 是 | PD/CC0/CC-BY/CC-BY-SA/CC-BY-NC(混合,逐图查) | 视具体图片许可而定(过滤掉 NC 的) | PD/CC0 免署名;CC-BY 系需署名"作者名 + 链接到 PhyloPic 许可页" |
| Wikimedia Commons(透明分类) | ✅ 是(但量少) | 逐文件不同,多为 CC-BY-SA/CC0/PD | 视具体许可 | 按文件页 `extmetadata` 里的 Artist/LicenseShortName 署名 |
| openclipart | ✅ 是(SVG 矢量) | 全站 CC0 | 可以 | 不需要(官方明确声明无需署名) |
| SVG Repo | ✅ 是 | 多为 CC0,个别另有许可 | 大部分可以商用免署名 | 按具体图标页说明为准,批量用前建议逐个核查 |
| Twemoji | ✅ 是 | CC-BY 4.0 | 可以 | 需要,如"Graphics by Twitter Twemoji, CC-BY 4.0" |
| Noto Emoji | ✅ 是 | Apache 2.0 | 可以 | 需保留许可声明,但对最终用户界面无强制署名展示要求 |
| BHL(古典博物画) | ❌ 否(纸张背景,需抠图) | 绝大多数 Public Domain(个别新卷慎用) | 可以(留意出版年份) | PD 通常无需署名,建议仍标注"来源:BHL, biodiversitylibrary.org" |
| iNaturalist 照片 | ❌ 否(实拍照片) | 逐张不同(CC0/CC-BY/CC-BY-NC 等) | 仅 CC0/CC-BY/CC-BY-SA 可用,NC 系不可商用 | 用返回的 `attribution` 字段原样署名 |
| Wikimedia Commons(常规照片) | ❌ 否 | 逐文件不同 | 视具体许可 | 按 `extmetadata` 署名 |
| GBIF occurrence 图片 | ❌ 否 | 逐条不同(常见 CC-BY/CC-BY-NC) | 视具体许可,注意可能比记录本身更严格 | 用 `rightsHolder` 字段署名 |

## 五、给"生物地球仪"项目的建议管线

```
目标物种列表(几百个)
    │
    ├─ 1) GBIF species/match 拿 usageKey
    │       │
    │       ├─ 2) PhyloPic resolve(gbif.org/species) 查节点
    │       │       └─ 有剪影 → 直接用 rasterFiles/vectorFile(已透明,CC0/PD 优先)✅ 完成
    │       │       └─ 没有 → 用同一物种的属/科节点再查一次(兜底)
    │       │
    │       └─ 仍没有剪影 →
    │               ├─ 3) iNaturalist taxa+observations(photo_license=cc0,cc-by,cc-by-sa)抓一张开放许可实拍图
    │               │       └─ 本地 rembg(isnet-general-use)抠图 → 效果不好的用 birefnet-general 精修
    │               └─ iNaturalist 也没有 → Wikidata P18 → Commons 代表图 → 同样丢 rembg 抠图
    │
    └─ 少数"重点展示物种" → 可选:手工从 BHL Flickr 挑一张古典博物画,裁切+抠图,做特色收藏款图标
```

批量脚本建议把每张图的**来源 URL、许可、署名文案**一起存进一个 JSON/CSV 清单,方便将来在网页里统一生成"图片来源"页(几乎所有非 PD/CC0 的源都要求署名,提前把这条数据管道打通比事后补救省事得多)。
