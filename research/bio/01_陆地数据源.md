## 0. 先读:验证方法说明(避免误判"能不能用")

本报告里每个数据源都标了两个独立维度,请按标签字面意思理解,不要混淆:

| 标签 | 含义 |
|---|---|
| **[已验证]** | 本次调研在调研用的云端环境里,直接用 `curl`/`WebFetch` 实测过——真的拿到了 HTTP 状态码、真实响应体(JSON字段/GeoJSON坐标/文件体积等),不是道听途说 |
| **[文献]** | 只在搜索结果摘要或第三方文档里见到过,本次没能直接拉到内容(常见原因:目标站有 Cloudflare/AWS WAF 机器人拦截,或调研环境网络异常) |
| **中国大陆可达性** | ⚠️ **这是推断,不是实测**——调研环境本身大概率不在中国大陆网络(是海外云region),所以"我这边能访问"只能证明"公网上这个 URL 是活的",**不能**证明"中国大陆直连能不能通"。下面的"可直连/需代理/未知"判断,依据的是域名归属的基础设施类型(Google 系一律判需代理;Cloudflare 防护站点历史上与 GFW 协议层有冲突、经常抽风;其余按常识判断)。**正式实施前务必自己用现有代理 `http://127.0.0.1:33210` 切换实测一遍**,不要直接信这份报告里的可达性结论去写死代码逻辑。

另外,调研过程中撞见一个重要的**技术可行性事实**(直接实测得出,不是猜的),先剧透在最前面,后面工程建议章节会展开:

> RESOLVE Ecoregions 2017 的官方 ArcGIS FeatureServer 可以直接查询导出 GeoJSON(不用注册),但**全量 847 个生态区在坐标精度降到约 1km 后,抽样 50 个就有 11.4MB**,全量估算在 150~200MB 量级——**不能直接怼给浏览器**,必须像本项目 `tools/build_borders.js` 处理历史疆界那样,导出后过一遍 mapshaper 简化到 1~3MB 量级才能用。这和本项目 README 里"巨型多边形拖垮逐帧 raycast"的坑是同一类问题,提前预警。

### 1.1 WWF Terrestrial Ecoregions of the World(Olson et al. 2001)

**引用文献**:Olson, D.M., Dinerstein, E., Wikramanayake, E.D., et al. (2001). "Terrestrial Ecoregions of the World: A New Map of Life on Earth." *BioScience*, 51(11), 933–938.

**核心数字**(经 Wikipedia 页面 [已验证] 抓取原文确认):地球陆地划分为 **8 个生物地理界(realms)**,下辖 **867 个生态区(ecoregions)**,每个生态区归入 **14 个主要生境类型之一(biomes)**。注意:常见第二手资料里出现的"825"这个数字,是部分 shapefile 发行版本里实际带几何面的生态区数量(剔除了南极/无主区等),867 是 Olson 论文里生态区命名总数,两个数字不矛盾,写代码时以你拿到的具体 shapefile 里的实际 feature 数为准。

### 1.2 RESOLVE Ecoregions 2017(WWF 更新版)—— 本报告首推数据源

**引用文献**:Dinerstein, E., Olson, D., Joshi, A., et al. (2017). "An Ecoregion-Based Approach to Protecting Half the Terrestrial Realm." *BioScience*, 67(6), 534–545.

这是 Olson 2001 的现代化升级版,由 RESOLVE(非营利组织)联合 WWF、多所高校在 2017 年发布,常规介绍为"846 个陆地生态区",实测数据服务返回的 feature 数是 **847**(差 1 大概率是几何切分/南极附属岛屿归并方式不同,不影响使用)。

| 项目 | 内容 |
|---|---|
| 可视化官网 | https://ecoregions2017.appspot.com/ (Google App Engine 域名) |
| **官方可直查 GeoJSON 的 API 端点**(重点发现) | `https://data-gis.unep-wcmc.org/server/rest/services/Bio-geographicalRegions/Resolve_Ecoregions/FeatureServer/0` (UNEP-WCMC 联合国环境规划署托管的 ArcGIS Server) |
| Google Earth Engine 版 | https://developers.google.com/earth-engine/datasets/catalog/RESOLVE_ECOREGIONS_2017 |
| 格式 | ArcGIS FeatureServer 原生支持导出:`sqlite, filegdb, shapefile, csv, geoJSON, kml`(REST 查询直接加 `f=geojson` 参数即可,无需下载整包再转换) |
| 体积 | 单个 feature 全精度约 20~300KB 不等(实测抽样);坐标精度降到 `geometryPrecision=2`(约 1km 级)后,847 个中的 50 个 = **11.4MB**,全量估算 **150~200MB**——见第 4 章工程建议,必须简化后再用 |
| 许可 | **CC-BY 4.0**(多个独立来源交叉确认一致) |
| 字段(实测 schema,直接可用于配色) | `eco_name`(生态区名)、`biome_num`/`biome_name`(所属生物群系编号/名称)、`realm`(生物地理界)、`eco_id`、`license`、`nnh`/`nnh_name`("Nature Needs Half" 保护状态分级)、**`color`/`color_bio`/`color_nnh`(官方预置的十六进制配色!直接能拿来给地球贴色,不用自己配色板)**、`ecoregion_area_km2` |
| 验证状态 | **[已验证]** 直接 `curl` 查询 `.../FeatureServer/0/query?where=1=1&returnCountOnly=true&f=json` 返回 `{"count":847}`;抓取单条 feature 的 `f=geojson` 输出确认是真实 MultiPolygon 坐标,不是占位数据 |
| 中国大陆可达性 | `data-gis.unep-wcmc.org`(联合国环境规划署世界保护监测中心,英国机构)—— 常规 REST 服务,推测可直连,建议实测;`ecoregions2017.appspot.com` 和 Earth Engine 目录是 **Google 域名,几乎确定需要代理** |

**直接可用的查询示例**(已实测跑通):

```
# 查 feature 总数
https://data-gis.unep-wcmc.org/server/rest/services/Bio-geographicalRegions/Resolve_Ecoregions/FeatureServer/0/query?where=1=1&returnCountOnly=true&f=json

# 导出精简字段 + 降精度的 GeoJSON(单页,注意 ArcGIS 默认 maxRecordCount=2000,847 条一次能出完,
# 但全精度会爆体积,务必带 geometryPrecision 且做好分页容错)
https://data-gis.unep-wcmc.org/server/rest/services/Bio-geographicalRegions/Resolve_Ecoregions/FeatureServer/0/query?where=1=1&outFields=eco_name,biome_num,biome_name,realm,color_bio&geometryPrecision=2&resultRecordCount=50&resultOffset=0&f=geojson
```

实测:不加分页、一次性拉全 847 条在 `geometryPrecision=2` 下会被服务端直接报 `500 Error performing query operation`(大概率是响应体过大或超时),**必须用 `resultOffset`/`resultRecordCount` 分页拉取后再本地合并**,这点务必写进下载脚本。

### 1.3 动物地理界(Zoogeographic Realms):Wallace 经典划分 vs Holt et al. 2013 现代修订版

**经典 Wallace(1876)**:19 世纪提出,8 大动物地理区(古北界/新北界/东洋界/古热带界/新热带界/澳大拉西亚界/大洋洲界/南极界),年代久远已进入公有领域,但**没有一份"官方权威"的现代地理边界数据文件**——网上能找到的都是各家博物学重绘版本,精度和边界划法不完全一一致,使用时需注明是"经典 Wallace 方案的现代重绘"。

**Holt et al. 2013 现代修订版**:

**引用文献**:Holt, B.G., Lessard, J.P., Borregaard, M.K., et al. (2013). "An Update of Wallace's Zoogeographic Regions of the World." *Science*, 339(6115), 74–78.

基于 21,037 种两栖类/鸟类/哺乳类的分布与系统发育关系重新聚类,得到 **11 个大界(realms)、20 个区(regions)**,是目前动物地理学界公认的现代权威版本。

| 项目 | 内容 |
|---|---|
| 数据托管页 | https://macroecology.ku.dk/resources/wallace (哥本哈根大学宏观生态学、演化与气候中心 CMEC) |
| 下载内容 | ① `CMEC regions & realms.kmz`(Google Earth 格式)② `CMEC regions & realms.zip`(Esri shapefile,11 界 + 20 区)③ `Taxon_Specific_regions.zip`(鸟类/哺乳类/两栖类分别的版本) |
| 格式 | KMZ + Shapefile |
| 体积 | 页面未标注具体大小,未下载实测 |
| 许可 | ⚠️ **页面原文只写"任何使用该地图必须注明来源 *Science* / AAAS",没有给出明确的 CC 许可协议**,重新分发/公开网页展示这份边界数据的权利边界不清晰 |
| 引用要求 | 必须标注 *Science* 期刊 / AAAS |
| 验证状态 | **[已验证]** 直接 WebFetch 该页面成功,确认三个下载文件名、格式、许可声明原文 |
| 中国大陆可达性 | `macroecology.ku.dk` 是丹麦哥本哈根大学域名,Apache 服务器,未检测到 Cloudflare/Google 特征,推测可直连,未实测 |

**工程建议**:如果项目对"能否公开重绘/redistribute"这条比较在意,Holt 2013 的授权表述偏保守,建议要么邮件跟 CMEC 确认一下允许范围,要么退回用经典 Wallace 8 界方案(公有领域、无版权顾虑,只是精度和现代生物学共识有差距)。

## 2. 物种分布数据 API

### 2.1 GBIF(Global Biodiversity Information Facility)—— 本报告首推的物种分布数据源

GBIF 是目前全球最大的物种出现记录聚合库,本次调研中**验证最充分、可用性最好**的数据源,强烈推荐作为"物种分布点/热力图"图层的第一选择。

#### 2.1.1 Occurrence Density Map Tiles API(重点)

| 项目 | 内容 |
|---|---|
| 端点模板 | `https://api.gbif.org/v2/map/occurrence/density/{z}/{x}/{y}@{1x,2x,3x,4x}.png?srs={SRS}&taxonKey={key}&bin={hex,square}&hexPerTile={n}&style={styleName}` |
| 能力探测端点 | `https://api.gbif.org/v2/map/occurrence/density/capabilities.json?taxonKey={key}` |
| 矢量瓦片 | 同一端点把 `.png` 换成 `.mvt` 即可拿 Mapbox Vector Tile |
| 投影支持 | `EPSG:3857`(默认/Web墨卡托)、`EPSG:4326`(经纬度)、`EPSG:3575`(北极 LAEA)、`EPSG:3031`(南极极射赤面) |
| 是否需要 Key | **不需要**,匿名可直接调用 |
| 是否需要注册 | 不需要 |
| 许可 | GBIF 聚合的每条底层数据集有各自独立许可(CC0 1.0 / CC BY 4.0 / CC BY-NC 4.0,由发布方选择),瓦片本身是聚合计数、非原始记录,常规可视化用途风险较低,建议按 GBIF 官方引用指引挂 "GBIF.org" 署名 |
| 验证状态 | **[已验证,实测跑通]**:`curl` 直接请求 `https://api.gbif.org/v2/map/occurrence/density/0/0/0@1x.png?srs=EPSG:4326&taxonKey=1&bin=hex&hexPerTile=57&style=classic.poly` 返回 `200`,真实 PNG,164,200 字节;`capabilities.json` 端点返回 `{"minLat":-90,"maxLat":90,...,"total":2861664777,...}`,即 GBIF 当前收录 **28.6 亿条**物种记录 |
| 中国大陆可达性 | `api.gbif.org` 子域(真正干活的接口)未见 Cloudflare/Google 特征;`www.gbif.org` 主站有 Cloudflare 拦截自动化请求(和地域无关,机器人质询),两者独立,**接口能通不代表官网能打开**,反之亦然 |

**GBIF 官方博客的实用范例**(已验证博客文章 `data-blog.gbif.org` 可直接访问,内容属实):

```
# Leaflet 直接挂瓦片图层
https://api.gbif.org/v2/map/occurrence/density/{z}/{x}/{y}@1x.png?style=scaled.circles&taxonKey=5219404

# 常用可视化风格(style 参数):classic.poly / scaled.circles / green.poly /
#   iNaturalist.poly / classic-noborder.poly / glacier.point 等
# source=density(预计算,快)vs source=adhoc(任意过滤条件,如 iucn_red_list_category=CR,较慢)
```

#### 2.1.2 Occurrence Search / Download API

| 项目 | 内容 |
|---|---|

## 4. 工程实施建议(针对本项目 globe.gl 架构)

结合本项目 `README.md` 里已经踩过的坑("历史疆界 GeoJSON 是逆时针外环,three-globe 要顺时针"、"巨型多边形拖垮逐帧 raycast,小邦烘进纹理"),给出以下具体建议:

### 4.1 框架色块层(biome/ecoregion 底色)

- **首选 RESOLVE Ecoregions 2017**(1.2节):字段自带 `color_bio` 官方配色,省去自己设计生物群系色板的功夫。
- **强制要做简化流水线**,复用本项目已有的 `tools/build_borders.js` 套路:① 分页从 `data-gis.unep-wcmc.org` 拉全量 GeoJSON(`resultOffset` 循环)② 过 `mapshaper -simplify` 砍到 1~3MB 量级 ③ 检查环绕方向是否要按 three-globe 要求翻转(和历史疆界那次一样,大概率也要处理)④ 小面积生态区依旧考虑烘进球面纹理而不是矢量图层,重蹈"raycast 卡死"的坑。
- 如果 3D 视觉上 867 个精细生态区显得太碎/太吵,退化用"14 个 Biome 溶解版"(见 3.2 节的思路,自己溶解,不要直接依赖第三方个人托管的那两份)。

### 4.2 物种分布层(点位/热力)

- **首选 GBIF density tile API**:瓦片天生分级加载、按需请求,不需要在客户端处理百万级坐标点,和 globe.gl 的纹理/瓦片加载模型天然契合,且不需要注册。
- 具体物种(如"熊猫分布"、"老虎分布")的精细边界如果要展示,再按需去 IUCN 单独下载对应 shapefile,但注意非商业限制和"不得 web 服务再分发"条款,建议做成静态摘要图/预渲染图片,而不是把原始矢量文件直接挂到公开仓库里长期分发。

### 4.3 气候分带层(可选叠加)

- Köppen-Geiger 用 **`climate_data_1p0.zip`(约27MB,1°精度)**这一档就够地球仪尺度使用,不要碰 1km 原始 GeoTIFF(125MB+),下载后本地重采样/上色转成小尺寸 PNG 纹理再入库。

### 4.4 动物地理界层(可选叠加,和植物系 biome 区分开的"动物学视角")

- Holt et al. 2013 数据能直接下载,但许可表述模糊("须注明来源 Science/AAAS",无明确 CC 协议),**上线前建议先邮件跟哥本哈根大学 CMEC 团队确认二次分发权限**,或者退而求其次用经典 Wallace 8 界(公有领域)方案。

### 4.5 优先级/性价比排序建议

1. GBIF 密度瓦片(现成 API,零下载,零许可顾虑,直接能接)
2. RESOLVE Ecoregions 2017(需要一次性 ETL + mapshaper 简化,长期收益最大,做成静态图层后不依赖外部服务)
3. Köppen-Geiger 1° 版(可选叠加层,体积可控)
4. IUCN/Holt 2013/CI hotspots(许可/权限都需要额外确认,建议排后面,先把前三个做完再评估要不要加)

## 6. 坑与注意事项汇总

1. **不要对 ArcGIS FeatureServer 一次性拉全量高精度 GeoJSON**——RESOLVE Ecoregions 847 条全精度直接查询会被服务端 500 报错拒绝,必须用 `resultOffset`/`resultRecordCount` 分页 + `geometryPrecision` 降精度,拉回来后再本地跑 mapshaper 简化,和本项目历史疆界那条流水线思路一致。
2. **官网 403 ≠ 数据不存在**——WWF、GBIF 主站、IUCN 引用指引页、CEPF、Map of Life API 这几个在本次调研里都返回了 403,但逐一排查后发现是 Cloudflare/AWS WAF 针对自动化请求的机器人质询(有的页面响应头直接写了 `Cf-Mitigated: challenge`),真人浏览器访问大概率正常,写爬虫/自动下载脚本时要预料到这类拦截,必要时手动下载一次存起来。
3. **IUCN 数据许可条款明确禁止"以 web 服务/API 形式二次分发"**——如果最终要把 IUCN 物种边界数据摆上公开网页长期展示,存在触碰条款的风险,建议做法是"仅做一次性静态可视化产出图/摘要统计"而不是"把原始矢量文件放进公开仓库"。
4. **Holt et al. 2013 动物地理界许可表述模糊**,只说"须署名 Science/AAAS",没有给出可执行的重分发条款,上线前最好邮件确认一次。
5. **xeno-canto 每条录音许可可能不同**,不能当作整库统一许可处理,要保留并展示每条记录的具体 CC 协议。
6. **v2 API 已死的例子**:xeno-canto v2 端点实测 404,网上还能搜到不少教程在讲 v2,照抄会直接踩坑,一律以 v3(`/api/3/`)为准。
7. **"中国大陆可达性"这栏本报告标的都是推断**,调研环境本身在海外网络,唯一能确认的是"公网上这个 URL 活着";Google 系域名(`appspot.com`、`developers.google.com/earth-engine`)基本可以确定需要代理,其余请上线前用 `http://127.0.0.1:33210` 代理开关各测一遍直连和代理两种情况,不要直接照抄这份报告的可达性结论写死降级逻辑。
